# WebLogic 中间件远程代码执行漏洞整改（CVE-2020-2798 / 2801 / 2828 / 2867）

## 问题

- 信息通报20-10期："Weblogic 中间件远程代码执行漏洞CVE-2020-2798、2801、2828、2867"
- 处置要求（作业结点）：
  - "1.在操作系统内查找weblogic路径：Windows：通过文件查找功能查找wls9_async_response.war与wls-wsat.war文件及相关文件夹；如果查找不到说明未采用。"
  - "2.查找到后进入文件所在路径，执行更名操作（windows直接重命名）"
- 受影响版本：
  - Oracle WebLogic Server 10.3.6.0.0
  - Oracle WebLogic Server 12.1.3.0.0
  - Oracle WebLogic Server 12.2.1.3.0
  - Oracle WebLogic Server 12.2.1.4.0
  - Oracle WebLogic Server 14.1.1.0.0
  - "如果当前版本在影响范围内，请及时进行更新。WebLogic 12.2.1.4官方下载地址：https://www.oracle.com/middleware/technologies/weblogic-server-downloads.html"

---

### 🔍 漏洞原理与风险

这四个 CVE 是 WebLogic 的**反序列化远程代码执行漏洞**，出自 Oracle 2020 年 4 月的关键补丁更新（CPU）。攻击路径走的是 T3 协议（CVE-2020-2798、2828）和 IIOP 协议（CVE-2020-2801、2867），默认监听端口 7001。

**原理**：WebLogic 的 T3/IIOP 通道默认接收序列化对象。攻击者不需要任何账号，直接向 7001 端口发一个精心构造的序列化请求，服务端反序列化时就会触发恶意代码执行。这类"链"在公开网络上已有完整利用代码，能被打包成自动化扫描工具批量打。

**后果**：WebLogic 进程以什么权限跑，攻击者就拿什么权限。Windows 上 WebLogic 通常以本地服务账号或管理员权限运行，一旦拿下，等于整台主机沦陷。OMS 这类主机处在电力监控系统网络里，单台被打穿后可以横向移动到其它监控主机，比互联网上的资产后果严重得多。

`wls9_async_response.war` 和 `wls-wsat.war` 是历史上多起 WebLogic 反序列化漏洞的入口组件（异步响应服务、WS-AtomicTransaction 服务）。业务上基本用不到它们，留着就是白送攻击面。所以通报里的处置思路是：**先找、再更名**，把入口堵掉。

### 处置方法

**第一步：定位 war 文件**

在 Windows 资源管理器右上角搜索框输入 `wls9_async_response.war`、`wls-wsat.war`，全盘查找这两个文件**及相关文件夹**。也可以用命令提示符在 WebLogic 安装目录下搜：

```text
dir /s /b wls9_async_response.war
dir /s /b wls-wsat.war
```

重点看两个位置：WebLogic 安装目录（`%WL_HOME%\server\lib` 之类）和域目录下各 Server 的展开部署目录（`servers\<服务器名>\tmp\_WL_internal\` 下同名文件夹）。域模式下 AdminServer 和每个 ManagedServer 都要查，不是只查一个。

如果全盘找不到，说明该主机未采用/未部署这些组件，这一条就可以直接闭环，记录"未采用"。

**第二步：更名**

进入文件所在路径，对 `.war` 文件直接右键重命名，建议追加 `.bak` 或 `.disabled`，例如：

```text
wls9_async_response.war  →  wls9_async_response.war.bak
wls-wsat.war             →  wls-wsat.war.bak
```

`tmp\_WL_internal\` 下已展开的同名目录也一并更名。只更名不删除，是为了出问题能快速回退。更名后需要**重启对应的 WebLogic 服务**（在 services.msc 里找到 WebLogic 实例服务重启，或停掉后重新运行 `startWebLogic.cmd` / `startManagedWebLogic.cmd`），让服务按新的文件名重新装载部署，改动才真正生效。

**第三步：版本更新**

更名只是缓解，不是根治。先确认当前 WebLogic 版本是否在受影响列表内（10.3.6.0.0 / 12.1.3.0.0 / 12.2.1.3.0 / 12.2.1.4.0 / 14.1.1.0.0），在范围内就要更新。查版本可以用管理控制台（`http://<主机IP>:7001/console`）首页查看，或在命令行执行：

```text
java -cp "%WL_HOME%\server\lib\weblogic.jar" weblogic.version
```

官方下载地址（12.2.1.4）：https://www.oracle.com/middleware/technologies/weblogic-server-downloads.html

### 特殊情况处理

- **业务确实依赖这两个组件**（用到异步响应或 WS-AT 事务）：直接更名会导致相关功能不可用。这种情况不要贸然动手，先跟业务方和厂家确认，安排在检修窗口内操作，并优先走打补丁/升级的路子，而不是靠更名。
- **更名后服务没重启**：war 文件更名了，但 `tmp` 下展开的旧副本还在跑，等于没处理。务必重启服务并检查展开目录。
- **集群环境**：只处理 AdminServer 会漏掉 ManagedServer，所有节点的对应目录都要查、都要更名。
- **回退**：如果更名后业务异常，把 `.bak` 改回原文件名，重启服务即可恢复。
- 更名前先备份：把原 `.war` 文件复制一份到独立目录留档，防止误操作。

### 📌 处置后的验证

- 再次在资源管理器或命令行全盘搜索两个文件名：`dir /s /b wls9_async_response.war`、`dir /s /b wls-wsat.war` → 不再出现原始文件名（只剩 `.bak` 更名后的文件）。
- 浏览器访问对应部署上下文（如 `http://<主机IP>:7001/_async/`）→ 返回 404 或无法访问，说明入口已关闭。
- 确认 WebLogic 版本：不在受影响版本列表内，或已升级到官方修复版本。
- 表单本项完成情况标 √。
