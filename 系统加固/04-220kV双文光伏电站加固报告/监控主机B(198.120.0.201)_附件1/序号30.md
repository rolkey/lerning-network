# 日志系统配置文件保护

## 问题

- "修改日志配置文件（syslog.conf）权限为400（管理员帐号只读）"
- 加固方法：执行 `Chmod 400 /etc/syslog.conf`，修改日志配置文件权限为 400，使管理员只读

---

### 🔍 风险原理

syslog 的配置文件决定"哪些日志记、记到哪里、转发给谁"。攻击者拿到普通用户权限后，如果这个文件可写，最省事的隐藏手段不是去删日志，而是改配置：把 `authpriv.*` 指向 `/dev/null`，把 `@loghost` 转发行注释掉——之后所有登录、认证事件直接消失，还不留删除痕迹。

把配置文件的权限收紧到 `400`（仅属主可读），普通用户连读都读不到，更谈不上写。这里要澄清"管理员只读"的实际含义：root 不受文件权限约束（特权账户绕过 DAC），`400` 约束的是属主之外的**非特权账户**，让它们既不能查看、也不能篡改配置内容。

### 配置加固方法

CentOS 7 使用 rsyslog，配置文件是 `/etc/rsyslog.conf`（老式写法 `/etc/syslog.conf` 在该版本上不存在）。执行：

```bash
chmod 400 /etc/rsyslog.conf
```

若主机上确实还存在 `/etc/syslog.conf`（老系统或迁移遗留），同样执行：

```bash
chmod 400 /etc/syslog.conf
```

rsyslog 还支持 `/etc/rsyslog.d/` 下的配置片段，建议一并收紧：

```bash
chmod 600 /etc/rsyslog.d/*.conf
```

确认属主为 root：

```bash
chown root:root /etc/rsyslog.conf
```

### 特殊情况处理

- **服务要能读**：rsyslog 以 root 启动，`400` 权限下可正常读取加载，不影响服务运行，改完重启即可验证。
- **别动日志文件本身**：本项收紧的是配置文件，不是 `/var/log/` 下的日志文件。日志文件权限由服务自身和 logrotate 管理，随意 chmod 可能破坏写入或轮转。
- **基线脚本查老路径**：如果现场检查脚本仍查 `/etc/syslog.conf` 而该文件不存在，向检查方说明系统为 CentOS 7，对应文件是 `/etc/rsyslog.conf`，权限要求等同执行。

### 📌 加固后的验证

```bash
ls -l /etc/rsyslog.conf
```

期望输出类似：

```text
-r-------- 1 root root 2054 10月  1 10:00 /etc/rsyslog.conf
```

权限位为 `r--------`（400），属主 root。

重启服务确认配置仍能正常加载：

```bash
systemctl restart rsyslog && systemctl status rsyslog
```

期望状态为 active (running)。
