# 处置 WebLogic async 反序列化漏洞

## 问题

> （1）禁止所有IP对weblogic的/_async/*和/wls-wsat/*目录进行访问。
>
> （2）删除wls9_async_response.war与wls-wsat.war文件及相关文件夹，并重启Weblogic服务。

---

### 🔍 漏洞原理与风险

WebLogic 中间件默认部署的两个组件存在反序列化漏洞：

- `wls9_async_response.war`，对外映射路径 `/_async/*`；
- `wls-wsat.war`，对外映射路径 `/wls-wsat/*`。

攻击者向这两个路径发送构造好的 SOAP/XML 请求，服务端在反序列化过程中执行攻击者代码，**无需认证即可远程执行命令**。WebLogic 进程通常以高权限账户运行，一旦被利用，攻击者直接拿到服务器控制权。

2019 年前后，这两个路径是被批量扫描、挖矿木马和勒索投放的重点目标。因为 `/_async/` 和 `/wls-wsat/` 默认就是开着的，全网扫描命中率极高。

这次处置的思路比打补丁更彻底：这两个组件业务上不用，直接禁止访问 + 删除组件文件，从根上把攻击面去掉。

### 处置方法

**第一步：禁止访问。**
在 WebLogic 前置的网关、防火墙或负载均衡上加 URL 拦截规则，禁止所有 IP 访问 `/_async/*` 和 `/wls-wsat/*`。主机层面也可以参照序号70的 IPSec/防火墙策略，对 WebLogic 控制台端口做访问来源限制。

**第二步：删除组件文件。**
1. 先停止 WebLogic 服务（`services.msc` 中找到对应 WebLogic 服务停止，或用域目录下的 `stopWebLogic.cmd` 脚本），避免文件被占用。
2. 用资源管理器搜索（或 `dir /s` 命令）定位 `wls9_async_response.war` 与 `wls-wsat.war`。它们一般位于 WebLogic 安装目录（如 `%WL_HOME%\server\lib`）以及域目录下 `servers\<服务器名>` 的 `tmp`、`stage` 等部署路径。
3. 删除这两个 war 文件及相关文件夹。
4. 同时清理部署缓存目录（如域下 `servers\<服务器名>\tmp\_WL_internal` 中对应的应用目录），防止重启时从缓存重新加载。

**第三步：重启 WebLogic。**
用 `services.msc` 重启 WebLogic 服务，或用 `startWebLogic.cmd` 脚本启动。重启后确认控制台正常。

### 特殊情况处理

- 如果业务确实依赖 wls-wsat 组件，不能直接删文件，应安装 Oracle 官方补丁并做最小化访问控制。本机按调度指令清单直接删除，说明业务不依赖这两个组件。
- 删除必须在停服状态下进行，否则文件被占用删不掉。
- 重启 WebLogic 需要运维窗口，期间控制台和部署在上的应用不可用，需提前通知相关系统。
- 删除后如果控制台仍能访问这两个路径，说明缓存没清干净，重新检查 tmp 目录。

### 📌 处置后的验证

- 浏览器访问 `http://<主机IP>:<控制台端口>/_async/`，应返回 404；同样方式验证 `/wls-wsat/` 返回 404。
- 确认 `wls9_async_response.war`、`wls-wsat.war` 及相关文件夹已不存在。
- WebLogic 服务重启成功，控制台可正常登录，业务应用运行正常。
