# fastjson Java 库执行漏洞

## 问题

> 信息通报20-9期：fastjson java 库执行漏洞（fastjson ≤ 1.2.67）
>
> 加固方法：
> 1. 在操作系统内查找 weblogic 路径：查找 fastjson 关键字。
> 2. 复制最新版 fastjson-1.2.58.jar 包到查询出来的相应目录，并删除掉受影响的 jar 包。

---

### 🔍 漏洞原理与风险

fastjson 是阿里的 Java JSON 序列化库，Java 平台的服务（包括 weblogic 上跑的业务）大量用它解析 JSON 数据。1.2.67 及之前的版本存在反序列化缺陷：攻击者提交一段特制的 JSON 数据，服务在解析过程中就会触发任意代码执行。市面上针对 weblogic 等中间件的攻击链，很多就是拿 fastjson 当突破口的。

fastjson 这类库平时藏在业务目录里，升级操作系统补丁根本碰不到它，所以必须专门去应用目录里翻。只要业务对外的接口会解析 JSON 数据，旧版 fastjson 就是一个现成的远程执行入口。OMS 主机上的 Java 平台如果带旧包，风险等级等同于被公开利用的中间件漏洞。

### 处置方法

**第一步：定位 fastjson jar 包**

1. 打开文件资源管理器，在 weblogic 安装目录及各业务应用的 lib 目录下搜索 `fastjson` 关键字，找出所有 `fastjson-*.jar` 文件。
2. 记录每个 jar 包所在目录，文件名中的数字就是版本号，例如 `fastjson-1.2.47.jar`。
3. 对照通报：版本 ≤ 1.2.67 的都属于受影响的包。

**第二步：替换并删除旧包**

1. 将最新版 `fastjson-1.2.58.jar`（及以上版本）复制到每个查找到的目录。
2. 删除该目录下受影响的旧 jar 包，避免新旧版本共存导致类加载混乱。
3. 重启对应的 weblogic 服务或业务应用，让新 jar 生效。

### 特殊情况处理

- 通报原文给的替换版本是 fastjson-1.2.58.jar，实际替换时以不含该漏洞的最新版本为准（不低于 1.2.58），不要反过来装更旧的包。
- 多个目录都搜到 fastjson 的，要全部替换，漏一个就等于没堵住。
- 替换后业务要做一轮功能回归：fastjson 版本差异可能导致某些序列化行为变化，先在内网验证再上正式环境。
- 如果 fastjson 被打包在厂商软件的 jar 里、无法单独替换，联系厂商发布升级补丁，不要强行解包修改。

### 📌 处置后的验证

- 重新搜索 `fastjson` 关键字，确认各目录下只剩新版本 jar 包，受影响的旧包已全部删除。
- 重启服务后查看启动日志无异常报错，业务应用能正常启动。
- 找一个正常业务接口发一次请求（或打开对应业务页面），确认功能正常后再确认处置完成。
