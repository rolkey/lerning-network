# Apache Tomcat AJP 协议文件读取/文件包含漏洞

## 问题

- "存在于 Tomcat 中的安全漏洞，由于 Tomcat AJP 协议设计上存在缺陷，攻击者通过 Tomcat AJP Connector 可以读取或包含 Tomcat 上所有 webapp 目录下的任意文件,例如可以读取 webapp 配置文件或源代码。此外在目标应用有文件上传功能的情况下，配合文件包含的利用还可以达到远程代码执行的危害"

---

这条漏洞（俗称 Ghostcat）2020 年初曝光时动静很大，因为它打的是 Tomcat 的 AJP 协议——一个几乎所有 Tomcat 都默认开着、却很少被关注的通道，默认监听 8009 端口。

### 🔍 漏洞原理与风险

**风险原理**：AJP 协议本来是给 Apache httpd 之类的反向代理和 Tomcat 之间通信用，Tomcat 对 AJP 通道传来的请求属性给予高度信任。缺陷在于：攻击者可以直接连上 AJP 端口，伪造一个带特殊属性的请求，让 Tomcat 把它当成"内部转发过来的请求"处理。于是本应只对内部 Web 应用开放的默认 Servlet 被外部请求触达，`webapp` 目录下的任意文件——`web.xml`、数据库配置文件、源代码——都能被读走。

**升级成 RCE 的路径**：如果目标应用恰好有文件上传功能，攻击者先上传一个特制文件（比如伪装成图片的 JSP），再利用文件包含能力把它当脚本执行，就拿到了远程代码执行。即使没有上传功能，配置文件泄露（数据库口令、密钥）本身也足够致命。

**为什么 AGC/AVC 环境要重点看**：厂商交付的 Tomcat 基本不改默认配置，8009 端口往往直接开着；而防火墙策略通常只盯 8080，8009 容易被漏掉。

### 处置/加固方法

先确认版本，落在影响范围内就更新：

```bash
# 定位并执行 Tomcat 自带的版本脚本
find / -name "version.sh"
sh /path/to/tomcat/bin/version.sh
```

受影响版本（源数据）：

- Apache Tomcat 6
- Apache Tomcat 7 < 7.0.100
- Apache Tomcat 8 < 8.5.51
- Apache Tomcat 9 < 9.0.31

**升级**：把 Tomcat 更新到 7.0.100 / 8.5.51 / 9.0.31 或更高版本，升级前备份 `conf/server.xml` 和业务 `webapps`。

**临时缓解（不能立即升级时）**：如果业务不依赖 AJP 转发，直接关掉 AJP Connector——编辑 `conf/server.xml`，把下面这段注释掉或删除：

```xml
<Connector port="8009" protocol="AJP/1.3" redirectPort="8443" />
```

保存后重启 Tomcat。关闭 AJP 不影响走 HTTP（8080）的业务。

### 特殊情况处理

- 有些架构用 httpd 的 `mod_jk`/`mod_proxy_ajp` 走 AJP 转发，直接关 AJP 会断业务。这种情况若必须保留 AJP：给 Connector 加 `secretRequired="true"` 并配置 `secret`（新版 Tomcat 默认强制），同时把 `address` 收紧到 `127.0.0.1`，只允许本机前端访问；升级计划照排，缓解措施不能当整改用。
- 无论是否保留 AJP，8009 端口都不该对非管理网段开放，主机防火墙层面顺手拦掉。
- Tomcat 6 已停止维护，没有修复版本可升，只能靠关闭 AJP + 网络隔离，并推动业务迁移到受支持的新版本。

### 📌 处置后的验证

```bash
# 1. 版本验证
sh /path/to/tomcat/bin/version.sh
# 期望：7.x ≥ 7.0.100 / 8.x ≥ 8.5.51 / 9.x ≥ 9.0.31

# 2. 端口验证（走临时缓解路线的）
ss -lntp | grep 8009
# 期望：无输出，8009 已不再监听
```

改完后重启 Tomcat，用业务页面做一遍完整回归；有条件的再用漏洞扫描器对 8009 端口复测一次。
