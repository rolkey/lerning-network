# fastjson Java 库反序列化漏洞（≤1.2.67）

## 问题

- "漏洞名称：fastjson java库执行漏洞
  【内容】对使用了fastjson java库的服务器采用以下策略：
  1. Fastjson 存在高危反序列化漏洞，影响版本1.2.30以下及1.2.41-1.2.45。修复建议：升级到1.2.58以上。
  【对象】fastjson"

---

fastjson 是阿里开源的 Java JSON 库，几乎每家 Java 应用都在用。它的反序列化漏洞不是"一次性"的：从 2017 年开始被反复绕过，修一版绕一版，1.2.67 及以下版本都有风险。这条通报要求至少升级到 1.2.58 以上。

### 🔍 漏洞原理与风险

**风险原理**：fastjson 为了支持把 JSON 直接还原成 Java 对象，默认开启了 autotype 机制——JSON 里的 `@type` 字段可以直接指定要反序列化成哪个类。攻击者构造一段带 `@type` 的恶意 JSON，指向某个危险的利用链类（比如能触发 JNDI 查询的类），服务端解析这段 JSON 时就会去加载攻击者指定的远程对象，从而执行任意代码。

**为什么反复修不好**：fastjson 一直在用黑名单拦危险类，攻击者就不断找名单外的新类绕过，双方来回拉锯。版本号落后越多的环境，风险越大。

**攻击路径**：任何把外部输入交给 `JSON.parseObject` / `parse` 处理的接口——登录、查询、上传参数都算——都可能被当成入口。AGC/AVC 系统的 Web 服务如果有对外接口，就是潜在攻击面。

### 处置/加固方法

整改三步：全盘找 jar → 换掉旧 jar → 重启中间件。

```bash
# 1. 在操作系统内查找 fastjson 相关的 jar 包
find / -name "*fastjson*"
# 如果返回相关的jar包，如 fastjson-1.1.20.jar 则为 1.1.20 版本，需要整改
# 假设路径为 /users/ems/tomcat_osb/webapps/fservice/WEB-INF/lib

# 2. 复制最新版 fastjson jar 到查询出来的目录，并删除掉受影响的旧 jar
cp fastjson-1.2.58.jar /users/ems/tomcat_osb/webapps/fservice/WEB-INF/lib/
rm /users/ems/tomcat_osb/webapps/fservice/WEB-INF/lib/fastjson-1.1.20.jar

# 3. 重启中间件服务
```

`find` 出来的每个位置都要处理，不止 Web 应用目录：Tomcat 的 `lib/`、WebLogic 的类库目录、独立 Java 程序的 classpath 里都可能藏着 fastjson。

### 特殊情况处理

- **业务系统对版本有依赖**：有些老应用写死了 fastjson 的 API 用法，换高版本可能启动报错。替换前先在备用环境做一次冒烟测试（启动 + 核心接口调用），再上生产。
- **多个应用共用同一个 fastjson jar**：优先升级共享的那份；如果有应用实在不能升，宁可给它们拆开用各自版本的 jar，也不要让 1.2.67 以下的版本继续解析外部数据。
- **短期无法升级的缓解**：fastjson 较新版本（1.2.68 起）提供 safeMode 开关和白名单配置，可以关闭 autotype；对外接口层面用 WAF 拦截带 `@type` 的请求。但按源数据要求，最终整改标准仍是升级到 1.2.58 以上——实际执行时建议直接采用官方当时的最新修复版本。

### 📌 处置后的验证

```bash
# 1. 确认旧 jar 已清理干净
find / -name "*fastjson*"
# 期望：不再出现 1.2.67 及以下的旧版本 jar，仅剩 1.2.58 及以上的新 jar

# 2. 重启中间件后检查启动日志无报错
# 3. 登录业务系统，把核心页面和接口过一遍
```

替换完成、业务回归正常，这条才算闭环。
