# 限制远程管理访问源地址

## 问题

- "配置访问控制列表，只允许堡垒机（I-II区1.1.1.5、1.1.1.6、III区3.1.1.5、3.1.1.6-7）、应用发布服务器（I-II区1.1.1.7、1.1.1.9，III区3.1.1.8、3.1.1.9）、态势感知服务器（I区态势感知1.1.1.3、II区态势感知2.1.1.3，III区态势感知3.1.1.3）能访问网络设备SSH管理服务。"

---

设备 SSH 管理服务即使开了强认证，理论上仍对网内任意主机开放。攻击者只要渗透进同一网段的任何一台普通主机，就能对网络设备发起登录尝试、口令爆破或针对 SSH 服务的漏洞探测。本项要求通过 ACL 把"谁能连上 SSH 管理口"收敛到一份白名单——只有堡垒机、应用发布服务器、态势感知服务器这些管理授权来源可以访问，其余来源一律拒绝。

### 🔍 风险原理

- **爆破面过大**：SSH 服务对所有主机开放时，任何被攻陷的终端都能充当爆破跳板，穷举口令、拖慢设备响应、触发账号锁定策略造成运维中断。
- **漏洞利用入口**：历史 SSH 实现曾出现各类协议漏洞，若管理服务暴露面过大，未授权主机也能触达这些漏洞，增加被远程利用的概率。
- **难以溯源**：不限定来源，登录日志里会出现大量来自陌生主机的失败尝试，干扰对真实攻击的判断；限定了白名单，任何白名单之外的连接请求都可直接视为异常。
- **纵深防御要求**：账号认证是第一道闸，来源 ACL 是第二道闸。即便口令泄露，攻击者若不在白名单主机上，依然无法建立连接，这是"最小化暴露面"的核心实践。

### 配置/加固方法

先定义一个基本 ACL 放行管理来源，其余默认拒绝，再把该 ACL 应用到 VTY 的入方向。

**1、创建基本 ACL 放行白名单（逐条 permit）**

```text
<H3C> system-view
[H3C] acl basic 2000
[H3C-acl-ipv4-basic-2000] rule 5 permit source 1.1.1.3 0
[H3C-acl-ipv4-basic-2000] rule 10 permit source 1.1.1.5 0
[H3C-acl-ipv4-basic-2000] rule 15 permit source 1.1.1.6 0
[H3C-acl-ipv4-basic-2000] rule 20 permit source 1.1.1.7 0
[H3C-acl-ipv4-basic-2000] rule 25 permit source 1.1.1.9 0
[H3C-acl-ipv4-basic-2000] rule 30 permit source 2.1.1.3 0
[H3C-acl-ipv4-basic-2000] rule 35 permit source 3.1.1.3 0
[H3C-acl-ipv4-basic-2000] rule 40 permit source 3.1.1.5 0
[H3C-acl-ipv4-basic-2000] rule 45 permit source 3.1.1.6 0
[H3C-acl-ipv4-basic-2000] rule 50 permit source 3.1.1.7 0
[H3C-acl-ipv4-basic-2000] rule 55 permit source 3.1.1.8 0
[H3C-acl-ipv4-basic-2000] rule 60 permit source 3.1.1.9 0
[H3C-acl-ipv4-basic-2000] quit
```

`0` 是反掩码，表示精确匹配单个主机。基本 ACL 末尾隐式 `deny any`，白名单之外的主机默认全部拒绝，无需再写 deny。

**2、将 ACL 应用到 VTY 入方向**

```text
[H3C] user-interface vty 0 4
[H3C-line-vty0-4] acl 2000 inbound
[H3C-line-vty0-4] quit
```

逐条说明：`acl 2000 inbound` 只作用于远程登录的入向流量；Console 口是物理本地接入，不走该 ACL，故不会被误拦。IP 清单中 I-II 区与 III 区网段不同（1.1.1.x / 2.1.1.x / 3.1.1.x），同一条 ACL 里用不同 rule 序号区分，序号只影响匹配先后，不影响最终放行结果。

### 特殊情况处理

- **IP 变更要同步 ACL**：堡垒机、态势感知服务器 IP 调整后，必须同步更新 ACL，否则管理会被"自己人"挡在门外，只能 Console 口救急。
- **先测再加 deny 心理预期**：基本 ACL 隐式拒绝一切未匹配流量，配置前务必把管理员的跳板机、堡垒机地址全部列入 permit，漏一个就锁一个。
- **VTY 范围全覆盖**：所有 `user-interface vty` 段都应用 `acl 2000 inbound`，若有扩展段（如 vty 5 15）也要一并配置。
- **与 SNMP ACL 区分**：本 ACL 管的是 SSH 登录来源；SNMP 有独立的 ACL（见序号25），两条 ACL 各自应用、不要混用。
- **注意反掩码写法**：Comware 基本 ACL 用反掩码，`source 1.1.1.5 0` 是单主机，不要误写成 `0.0.0.0`（那是匹配任意主机，会把 ACL 放宽成全放行）。

### 📌 加固后的验证

```text
<H3C> display acl 2000
```

期望结果：能列出上述 12 条 `permit source <IP> 0` 规则，无多余的 permit any。

```text
<H3C> display user-interface vty 0 4
```

期望结果：VTY 显示 `ACL: 2000` 且方向为 inbound。

验证效果：从白名单内主机（如堡垒机 1.1.1.5）SSH 可正常登录；从白名单外主机尝试 SSH，连接被拒绝、无登录提示。
