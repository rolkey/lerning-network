# 口令策略：复杂度、期限与登录失败锁定

## 问题

- "启用密码复杂性要求。设置口令的最长使用期限180天，最短1天，密码过期前28天做提醒；密码最小长度8位。不存在空口令帐号。
  3级系统应配置登录失败账号锁定策略：连续输错5次，密码帐号锁定30分钟。"

---

口令是监控主机防御体系里最后一道常开的门。默认口令、空口令、多年不改的口令，在变电站里比比皆是——很多主机从投运那天起就没动过密码。这条作业项把口令策略一次定死：复杂度要启用、长度至少 8 位、有效期 180 天、最短使用 1 天、过期前 28 天提醒，空口令清零，并且连续输错 5 次锁定 30 分钟。

### 🔍 风险原理

- **弱口令/默认口令**：`root/root`、`test/test` 这类口令是爆破字典的第一梯队，秒破；
- **空口令**：`/etc/shadow` 口令字段为空，意味着登录不需要口令，任何人（包括远程）都能直接进来；
- **口令永不过期**：口令一旦泄露长期有效，离职人员、外包人员掌握的口令一直能进系统；
- **无登录失败锁定**：攻击者可以无限次尝试口令（在线爆破），配合弱口令词典几乎必中。

源文给的锁定参数：`deny=5`（连续错 5 次锁定）、`unlock_time=1800`（锁定 1800 秒，即 30 分钟）。

### 配置/加固方法

**1、检查现状**

```bash
# 查看口令期限相关参数
more /etc/login.defs
# 检查 PASS_MAX_DAYS / PASS_MIN_LEN / PASS_MIN_DAYS / PASS_WARN_AGE 参数

# 检查是否存在空口令帐号（口令字段为空的行）
awk -F: '($2 == "") { print $1 }' /etc/shadow
```

同时按源文要求询问管理员是否存在类似简单口令配置：`root/root`、`test/test`、`root/root12345678` 之类，有则改掉。

**2、修改 /etc/login.defs 口令期限参数**

```bash
vi /etc/login.defs
# 按 i 编辑以下项目：
PASS_MAX_DAYS 180   # 密码最长使用天数 180 天（源文标注可选）
PASS_MIN_DAYS 1     # 密码最短使用天数 1 天（防止立刻改回旧密码）
PASS_WARN_AGE 28    # 密码到期提前 28 天提醒
PASS_MIN_LEN 8      # 密码最小长度为 8
```

已存在账号的期限参数不会自动跟着变，需要对存量账号单独设置：

```bash
chage -M 180 -m 1 -W 28 root
chage -M 180 -m 1 -W 28 admin
```

**3、启用密码复杂度（CentOS 7）**

源文写"执行 /etc/pam.d/system-auth"，即通过 PAM 模块控制复杂度。CentOS 7 用 `pam_pwquality`（由旧 `pam_cracklib` 演进而来），配置在 `/etc/security/pwquality.conf`：

```bash
vi /etc/security/pwquality.conf
minlen = 8          # 最小长度 8 位

vi /etc/pam.d/system-auth
password requisite pam_pwquality.so try_first_pass local_users_only retry=3
```

注意：启用了 PAM 的 CentOS 7 上，`login.defs` 里的 `PASS_MIN_LEN` 并不生效，长度要求由 `pam_pwquality` 的 `minlen` 决定，两边都要配。

**4、配置登录失败锁定（源文配置保留）**

```bash
# 3级系统应配置登录失败账号锁定策略：连续输错5次，锁定30分钟
vi /etc/pam.d/system-auth
# 修改 auth 段为：
auth required pam_env.so
auth required pam_tally.so onerr=fail deny=5 unlock_time=1800
auth sufficient pam_unix.so nullok try_first_pass
auth requisite pam_succeed_if.so uid >= 500 quiet
auth required pam_deny.so
```

逐行说明：

- `pam_tally.so deny=5 unlock_time=1800`：核心锁定逻辑，累计失败 5 次锁 1800 秒；
- `onerr=fail`：模块出错时按失败处理，宁可锁死不可放过；
- `pam_unix.so`：口令验证本体，`sufficient` 表示验证通过即不再往下走；
- `pam_succeed_if.so uid >= 500 quiet`：只有 uid≥500 的普通账号走上述验证，系统服务账号跳过；
- `pam_deny.so`：兜底拒绝。

**CentOS 7 注意**：`pam_tally.so` 在 CentOS 7 已废弃，对应模块是 `pam_tally2.so`（7.0 起默认存在），7.2+ 更推荐 `pam_faillock.so`，语义相同。另外 `uid >= 500` 是旧发行版习惯，CentOS 7 新建普通账号从 uid 1000 起，建议改成 `uid >= 1000`。`nullok` 表示允许空口令，与"不存在空口令账号"的要求冲突，应去掉：

```bash
# CentOS 7 等价写法（pam_faillock）
auth required pam_faillock.so preauth audit silent deny=5 unlock_time=1800
auth sufficient pam_unix.so try_first_pass
auth [default=die] pam_faillock.so authfail audit deny=5 unlock_time=1800
auth required pam_deny.so
```

### 特殊情况处理

- 源文把 `PASS_MAX_DAYS 180` 标了"可选"：现场可结合运维制度调整，但合规检查通常按 180 天上限核对，改动前先跟调度安全管理部门确认。
- 部分应用厂商账号（如监控系统内置账号）设了简单口令且不让改，要向厂商索取整改支持，不能因为"怕业务断"就豁免。
- 锁定策略生效后，堡垒机或监控平台批量试连错误密码也会触发锁定，注意先把这些平台的凭据同步成正确口令，避免自己被锁在门外。
- 口令到期提醒依赖登录场景；不常登录的主机靠运维排期主动轮换口令。

### 📌 加固后的验证

```bash
# 1、确认期限参数已生效
grep -E '^PASS_(MAX_DAYS|MIN_DAYS|WARN_AGE|MIN_LEN)' /etc/login.defs
# 期望：PASS_MAX_DAYS 180 / PASS_MIN_DAYS 1 / PASS_WARN_AGE 28 / PASS_MIN_LEN 8

# 2、确认空口令账号已清零
awk -F: '($2 == "") { print $1 }' /etc/shadow
# 期望：无任何输出

# 3、抽查 root 的密码期限
chage -l root
# 期望：最长/最短使用天数、提醒天数分别为 180 / 1 / 28

# 4、实测锁定策略：用错误口令连续尝试 5 次后，第 6 次即使口令正确也应被拒
# （pam_tally2 可查看失败计数）
pam_tally2 --user admin
```

期望结果：期限参数符合 180/1/28/8；空口令检查无输出；错误口令连续 5 次后账号锁定 30 分钟，期间正确口令也无法登录。
