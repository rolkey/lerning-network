# 静态口令密文存储

## 问题

- "若可使用SSH登录管理，查看配置文件，静态口令以密文形式存放。"

---

口令到底以什么形式存在防火墙里，直接决定了"配置文件泄露"时的危害程度。如果口令以明文保存，任何能导出或看到配置的人（包括越权管理员、备份文件外泄后的拾取者）都能直接读到明文口令。本作业项要求：所有静态口令（管理账号、SNMP 团体字、VPN 预共享密钥等）必须以密文/摘要形式存储，导出配置时也不得出现明文口令。

### 🔍 风险原理

- **配置泄露即口令泄露**：防火墙配置文件是备份、巡检、交接的常规对象，流动环节多。若口令明文存储，配置一旦外泄，攻击者无需破解即可直接获得管理口令。
- **越权与内部威胁**：一个只应有"只读策略"权限的低权限账号，如果导出的配置文件里躺着明文口令，就能变相获得本不该有的登录能力，权限隔离被击穿。
- **口令一致性风险**：明文口令容易被看到、被抄录、被复用，导致同一口令在多个设备间"串用"，一处泄露全处沦陷。
- **备份介质外流风险**：配置文件常被拷贝到 U 盘、网盘做备份，明文口令随备份介质流转，泄露面成倍扩大。

采用单向哈希（如 SHA-256、PBKDF2、bcrypt）或厂商加密算法存储口令，即使配置文件泄露，攻击者也无法直接还原明文。

### 配置/加固方法

**1. 确认口令存储方式**

通过 SSH 登录防火墙命令行，导出并查看配置文件中的口令字段，确认不是明文：

```text
# 逻辑示意（各厂商命令不同，以下为通用思路）：
# 登录后导出配置文件并检索口令相关字段
show running-config        # 查看运行配置
show configuration users   # 查看用户口令存储形式
```

```text
检查要点：
  admin 用户的口令字段应显示为 $1$...（MD5）、$5$...（SHA-256）、
  $6$...（SHA-512）或厂商私有密文，而非可读的明文字符串；
  SNMP 团体字、VPN 预共享密钥同理，不应以明文出现。
```

**2. 如发现明文，改用加密/摘要存储**

```text
操作路径（通用）：
系统管理 → 用户管理 → 修改口令：
  选择"加密存储/哈希存储"（部分设备默认即为密文，需确认未被降级）；
  对 SNMP、VPN 等敏感参数优先使用支持密文/加密的配置方式；
  必要时升级固件到支持口令加密的版本（3.2.4 应已支持）。
```

**3. 控制配置文件访问权限**

```text
配置文件属敏感资产：
  导出备份时选择"加密备份"选项；
  备份文件本地加密存放，禁止明文外发；
  限制"导出配置"权限仅授予管理员角色。
```

**4. 建立口令加密基线并巡检**

```text
将"口令密文存储"纳入周期性安全检查项，
定期导出配置抽查口令字段，防止配置迁移、升级后被改回明文。
```

### 特殊情况处理

- 部分老固件口令字段可能显示为可逆加密（非单向哈希），虽非明文但可被反向还原，应推动升级并改用单向哈希。
- 配置文件里即使口令是密文，也仍属敏感信息，不要因为"已加密"就放松备份文件的保管。
- 迁移/升级后需重新核查，某些升级过程会回退口令存储方式为明文，务必在升级后复验。
- 通过堡垒机代登的场景，防火墙本地账号口令仍应密文存储，不得因"有堡垒机兜底"而放松。

- 定期更换口令时，确认新口令仍以密文存储，避免手工在配置里写明文临时口令后忘记清除。
- 第三方厂家远程配置后，应复检其是否遗留明文口令或调试账号。

- 设备支持"口令回显掩码"时，界面上输入的明文口令也不应被日志或屏幕录制记录，避免二次泄露。

### 📌 加固后的验证

```text
# 验证要点
1. SSH 登录后导出配置文件，检索 user/admin 相关字段，确认口令为密文/哈希（含 $、!、* 等前缀标识）而非明文；
2. 检索 SNMP、VPN 预共享密钥字段，同样无明文；
3. 备份导出时能选择加密方式，导出文件用文本工具打开看不到明文口令。
```

期望结果：配置文件中所有静态口令均以密文或单向摘要形式存放，导出配置不含任何明文口令。
