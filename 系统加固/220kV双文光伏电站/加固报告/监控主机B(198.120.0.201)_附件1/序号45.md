# WebLogic async / wls-wsat 组件漏洞处置

## 问题

> 漏洞编号：调度20190615-001 —— weblogic中间件async漏洞
>
> 加固方法：（1）禁止所有IP对weblogic的/_async/*和/wls-wsat/*目录进行访问。（2）删除wls9_async_response.war与wls-wsat.war文件及相关文件夹，并重启Weblogic服务。

---

### 🔍 漏洞原理与风险

`/_async/*` 对应 WebLogic 的异步响应组件（AsyncResponseService），部署包是 `wls9_async_response.war`；`/wls-wsat/*` 对应 WS-AT（Web Services Atomic Transaction）事务服务，部署包是 `wls-wsat.war`。

这两组 URL 是 WebLogic 系列未授权远程代码执行问题的高发区。这类漏洞的典型利用路径是：攻击者在**未认证**的情况下，向这两个接口构造特制请求，触发 Java 反序列化或服务端注入，进而以 WebLogic 进程权限（通常是高权限账户）执行任意命令，最终拿下整台主机。整个过程不需要任何口令，只要网络可达就能打。

对调度、监控这类业务来说，async 和 wls-wsat 组件几乎都不是必需功能，所以作业的标准处置思路不是等补丁，而是**关入口、移部署包**——入口在网络侧封锁，部署包在主机上改名退役，双管齐下。

### 处置/加固方法

第一步，确认主机上到底有没有部署这两个组件：

```bash
find / -name wls9_async_response.war 2>/dev/null
find / -name wls-wsat.war 2>/dev/null
```

如果没有输出，说明这台主机未部署这两个组件，不用处理。

第二步，查找到文件后进入所在目录，执行改名。改名等效于让 WebLogic 不再加载该应用，同时 `.bak` 文件留着，方便回退：

```bash
mv wls9_async_response.war wls9_async_response.war.bak
mv wls-wsat.war wls-wsat.war.bak
```

第三步，重启 WebLogic 服务让改动生效（在 WebLogic 域目录的 `bin` 下执行，路径按实际安装调整）：

```bash
./stopWebLogic.sh
./startWebLogic.sh
```

另外，作业要求"禁止所有IP对 /_async/* 和 /wls-wsat/* 目录进行访问"，这一条通常在网络边界设备（防火墙/安全设备）上落实。如果本机需要兜底，可以用 iptables 收紧 WebLogic 监听端口的来源地址，但生产环境优先在网络侧做。

### 特殊情况处理

- 部分老版本 WebLogic 除了 war 包，还可能存在已经解压出来的同名应用目录，改名 war 的同时，同目录下的展开文件夹也要一并改名。
- 如果业务确实依赖 wls-wsat 事务功能（和第三方系统做事务级集成才会用到），不能直接退役，要改走"限制来源 IP + 打官方补丁"的路子。
- 改名操作本身可逆，出问题把 `.bak` 改回原名重启即可回退。
- 生产环境重启 WebLogic 前确认有停机窗口，重启动作会导致服务短暂中断。

### 📌 处置后的验证

- 再次执行 `find / -name 'wls9_async_response.war' 2>/dev/null` 和 `find / -name 'wls-wsat.war' 2>/dev/null`，应当无输出（只剩 `.bak` 文件）。
- 浏览器访问 `http://<主机IP>:<端口>/_async/` 和 `http://<主机IP>:<端口>/wls-wsat/`，应当返回 404 或页面不存在。
- 确认 WebLogic 进程已重新拉起：`ps -ef | grep java | grep weblogic`。
