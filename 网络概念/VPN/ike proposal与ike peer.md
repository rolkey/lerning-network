在 IKE（互联网密钥交换）的配置中，**IKE Proposal（安全提议）** 与 **IKE Peer（对等体）** 是“**被包含与引用**”的关系。简单来说，**IKE Peer 是通信的“对象”，而 IKE Proposal 是双方协商时必须遵守的“规则清单”**。IKE Peer 通过引用一个或多个 IKE Proposal，来指定与特定对端建立连接时所需的安全参数。

### 🛡️ IKE Proposal：定义协商规则
IKE Proposal 是一组用于保护 IKE 协商本身（即第一阶段）的安全参数集合。它本身并不指向任何具体的 IP 地址，只定义“用什么算法和参数来谈”。

*   **核心参数**：通常包含加密算法（如 3DES、AES）、认证方法（如预共享密钥、证书）、认证算法（如 MD5、SHA）、Diffie-Hellman 组（决定密钥交换强度）以及 SA 生存时间。
*   **优先级机制**：每个 Proposal 都有一个编号，**编号越小优先级越高**。发起方会发送 Proposal，响应方则按优先级从高到低在自己的 Proposal 列表中寻找匹配项。只要有一组参数完全一致，协商即可成功。

### 👥 IKE Peer：定义通信对象
IKE Peer 代表了一个具体的远端设备（即对端网关）。它负责“找到谁”以及“怎么连”，主要包含对端的地址、身份信息以及引用的 Proposal。

*   **核心功能**：它通常配置了远端 IP 地址、预共享密钥（如果使用 PSK 认证）以及本端身份标识等。
*   **与 Proposal 的联动**：IKE Peer 的核心作用之一就是**绑定** Proposal。你可以在 IKE Peer 视图下，通过命令引用一个或多个已经定义好的 IKE Proposal。

### 🔗 两者如何协同工作
在实际协商过程中，两者的配合逻辑如下：

1.  **发起方（Initiator）**：如果 IKE Peer 中**引用了**特定的 Proposal，那么发起方就只发送被引用的那些 Proposal；如果**没有引用**，则默认发送本端所有已配置的 Proposal（野蛮模式下仅发送默认 Proposal）。
2.  **响应方（Responder）**：收到发起方的 Proposal 后，会拿自己本端存在的所有 Proposal（无论是否被 Peer 引用）去按优先级逐一匹配，直到找到完全匹配的参数组。

**简单记忆**：**IKE Peer** 决定了“**跟谁谈**”（IP/身份），**IKE Proposal** 决定了“**谈什么条件**”（算法/密钥）。没有 Proposal，Peer 不知道用什么规则保护连接；没有 Peer，Proposal 也不知道该把这些规则用在与谁的通信上。
