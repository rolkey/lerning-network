- 感觉配置acl的时候通过源与目的IP的配置，也可以达到策略路由的效果，策略路由相对于acl有哪些特点与优势

---

这个问题的关键，在于**把"匹配条件"和"转发决策"分开看**——你感觉"ACL 配源+目的也能分流"，其实差了最后一层。

## 先破题：ACL 只输出"是/否"，不输出"从哪走"

ACL 本质是**分类器**：给它一个报文，它回答"命中 / 不命中"（permit / deny）。它自己不会说"这个包从 GE1/0/1 出去、下一跳 200.0.0.2"。

所以凡是"ACL 看起来做到了分流"，一定是它被**挂到了某个带动作的功能上**：

- 老式华为写法：`policy-based-route ... if-match acl 3000` + `apply ip-address next-hop 10.1.1.2` —— 这**就是 PBR**，ACL 只是它的 `if-match` 输入 
- MQC 流策略里 `redirect ip-nexthop`，华为官方直接注明"重定向到下一跳有时也被称为策略路由 PBR" 
- 安全策略 / NAT 策略里用 ACL 式条件匹配源目的，动作是放行、拒绝或地址转换，不是选出接口

换句话说：**ACL 是 PBR 的零件，不是 PBR 的对手**。在你那台 USG6000V1 上更直观——Web 里"新建策略路由"的匹配条件长得跟 ACL 一模一样（源地址、目的地址、服务），真正的分水岭是**动作栏**：`action pbr egress-interface GE1/0/1 next-hop 200.0.0.2`。有这句才是策略路由，没这句就只是一组条件。

---

## 一个例子戳破"源+目的也能达到"

内网两个网段，都要访问**同一个**外网地址 `203.0.113.9`：

- 财务 `192.168.10.0/24` → 走专线 ISP1
- 办公 `192.168.20.0/24` → 走宽带 ISP2

你写两条 ACL：

```text
rule permit ip source 192.168.10.0 0.0.0.255 destination 203.0.113.9 0
rule permit ip source 192.168.20.0 0.0.0.255 destination 203.0.113.9 0
```

然后呢？设备认出了这两条流，但**查路由表时目的地址完全相同**，到 `203.0.113.9` 只有一条最优路由（或两条等价路由做 hash）。结果要么两个部门走同一出口，要么随机分摊——**源地址根本没进入选路计算**。

想靠"把目的 IP 写细静态路由"模拟？目的相同，写不出来。这正是路由表的天花板：它的选路键只有目的地址。PBR 的定义就是"在路由表已经产生的情况下不按路由表转发，用入接口、源安全区域、源/目的 IP、用户、服务、应用等维度决定转发方向，优先于路由表生效" 。华为智能选路里的查询顺序也写死为：**策略路由 → 明细路由 → 缺省路由** 。

> 一句话：**目的不同，用明细路由就能分流，ACL/PBR 都多余；目的相同、源不同，路由表无解，只能上 PBR。** 你感觉"ACL 也能做到"的场景，基本都落在前一种。

## 对比一览

| | ACL（单独用） | 目的静态/动态路由 | 策略路由 PBR |
|---|---|---|---|
| 输出 | permit / deny（布尔） | 出接口 + 下一跳 | 出接口 + 下一跳 + 主备/负载/优先级 |
| 选路键 | 不参与选路 | **仅目的 IP** | 源/目的 IP、入接口、源安全区域、用户、服务、应用、域名组、运营商地址集  |
| 能否按"源"分流 | 不能 | 不能 | **能**（核心价值） |
| 链路故障 | — | 路由协议收敛 / 静态路由不动 | 绑定 IP-Link / 健康检查，主链路 down 后策略失效、回退备份路由  |
| 未命中时 | 取决于挂载模块（可能丢包） | 继续查表 | 自动回退路由表，默认路由仍兜底 |
| 规则组织 | 散落在多个模块里 | 全局一张表 | 独立规则列表，从上往下命中即停，可移动/启停/看命中次数  |

## PBR 真正的优势在哪

**1. 把"源"变成选路键**
这是它不可替代的唯一理由。同一目的、不同来源走不同路，路由表结构上就表达不了。

**2. 匹配维度超出 ACL 的能力边界**
传统 ACL 是 L3/L4 五元组 + DSCP。防火墙 PBR 能直接按**源安全区域、用户/安全组、应用识别、域名组、ISP 地址集**建规则——"视频会议走低时延专线、P2P 走廉价大带宽"这类需求，ACL 写不出来。（提醒一个上一轮提过的限制：首包时应用尚未识别，且策略路由不支持策略重查，所以基于应用的规则可能出现首包不命中，别把它当五元组用。）

**3. 动作是"链路编排"，不只是改个下一跳**
- 出接口 + 下一跳**绑定指定**，避免多出口下 ARP 错口
- 多下一跳做主备、按优先级/权重/带宽过载阈值智能选路
- `track healthcheck` / IP-Link 联动，链路挂了自动失效回退——**纯 ACL 写死的条件没有任何健康感知**；MQC 重定向到下一跳官方也明确说"本身没有检测机制，需与 NQA 联动" 
- 排在目的 NAT 之后、源 NAT 之前，easy-IP 会自动跟着新出接口变，双出口下不用手工改 NAT 

**4. 语义是"改道"而不是"拦截"**
用 ACL 模拟分流有个常见野路子：写 deny 把某出口"堵住"逼流量走另一条。这是过滤不是选路——链路故障时不会自动回退，规则一写宽就误杀。PBR 的规则表里每条都是"谁 → 从哪走"，未命中兜底路由表，fail-safe 是内建的。

**5. 排障可观测**
Web 上直接看每条策略路由的**命中次数**、上下移动调顺序、单条启用/禁用；`display firewall session table verbose` 能反查实际出接口。用 ACL 拼出来的方案，条件散在安全策略、NAT、路由策略好几处，出问题时得逐个模块翻。

---

## 什么时候别用 PBR（说句实在的）

PBR 不是越多越好，这三个条件**同时成立**才值得上，少一个都有更省事的办法：

1. 有**两条以上出口**，且都能到、但用途/成本/质量不同
2. 分流依据**路由表表达不出来**（源地址、部门、用户、应用、入区域）
3. 确实需要按业务指定路径，而不是单纯放行/阻断

- 只按目的地址分流 → 明细路由 / ISP 路由 / 全局智能选路更干净
- 只是放行或拒绝 → 安全策略 + ACL 就够
- 只是做地址转换 → NAT 策略

另外它优先级太高、又只对首包生效，是排障时最容易被忽略的一层：策略/NAT/路由只在建会话那一刻走一遍，改完 PBR 不 `reset firewall session table`，老连接看着就像"没生效" 。写宽一条 `any → 指定出口`，路由协议算出来的最优路径就全白算了。

---

## 小结

**ACL 回答"这个包是不是这类流量"，PBR 回答"这类流量从哪个口、哪个下一跳出去"。** 你看到的"ACL 也能分流"，要么是目的地址本来就不同（明细路由即可），要么是 ACL 被 PBR / MQC 重定向调用了——功劳在动作，不在 ACL。PBR 相对它的真正增量只有三样：**按源/用户/应用选路、带健康检查的链路编排、未命中自动回退路由表**。
